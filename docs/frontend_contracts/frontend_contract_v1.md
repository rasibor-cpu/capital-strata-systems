# CSS Institutional Frontend Payload Contract (v1.0.0)

## Overview
This document specifies the canonical, strict, versioned contract for frontend payloads generated by the CSS `DashboardState`. 
It ensures stability, safe deserialization, and prevents schema drift between the engine and the read-only Web Broker Control Center (or mobile apps).

## Contract Versioning
- **CONTRACT_NAME**: `CSS Institutional Frontend Payload`
- **CONTRACT_VERSION**: `1.0.0`
- **FRONTEND_CONTRACT_SCHEMA**: `css.frontend.contract.v1`

## Section Manifest
The payload is divided into canonical sections. All sections must be present, though their values can be empty or default.
- `account_summary`: Cash, equity, margin, account mode.
- `positions`: Open symbols, quantities, and individual PnL.
- `pnl_summary`: Realized and unrealized PnL, win rates.
- `risk`: Gate statuses, daily loss limits, exposure limits.
- `governance`: System locks, defensive modes.
- `market`: Regimes, volatility, spreads.
- `execution`: Slippage costs, recent trades.
- `opportunities`: Trade signals and probabilities.
- `broker`: Connection status, readiness.

## Websocket Event Types
Instead of a generic `dashboard_delta`, websocket deltas yield explicit, typed events:
1. `pnl_update` (When `pnl_summary` changes)
2. `position_update` (When `positions` changes)
3. `governance_alert` (When `governance` changes)
4. `execution_alert` (When `execution` changes)
5. `broker_status` (When `broker` changes)
6. `risk_update` (When `risk` changes)

## Guarantees & Safety
- **No Direct Broker Calls:** The frontend may only consume this payload.
- **Credential Redaction:** Keys such as `api_key` or `secret` are intercepted by the serializer and replaced with `"REDACTED"`.
- **Decimal Safety:** All `Decimal` objects from the ledger are strictly converted to floats or string representations before leaving the runtime.
- **Paper-First Safety:** The `resolved_mode` mandates that live trading is only possible if both the session and the underlying broker explicitly agree.

## Deprecation Policy
- Changes to keys within sections must be additive. 
- Removing a key requires a major version bump.
- Structural payload changes require formal review via PCNRASS.
