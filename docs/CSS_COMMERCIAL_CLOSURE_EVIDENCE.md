## Control evidence

**RBAC.** Grants live in `backend/security/permissions.py` (`COMMERCIAL_ROLE_GRANTS`). FINCON prepares; HEAD_FINCON and HEAD_COMPLIANCE approve; FINCON, AUDIT and COMPLIANCE view; audit history is limited to AUDIT, HEAD_AUDIT, HEAD_FINCON and HEAD_COMPLIANCE. SUPER_USER, ADMIN, TECH and trading roles get no commercial rights. Tests assert that a missing actor, identity or role, an unknown role, an unknown action and role-string escalation are all denied (`tests/test_commercial_controls.py`), and that every API route returns 403 for non-commercial and superuser sessions (`tests/test_commercial_governance_api.py`).

**Maker-checker.** `engine/commercial/commercial_controls.py`. Enforced properties, each with tests:
- maker ≠ checker;
- checker holds approve permission;
- replayed and concurrent approvals are rejected (compare-and-set; one success and one 409 under a forced race);
- stale or manipulated approvals are rejected by payload-hash mismatch;
- approval after an incompatible state change is rejected;
- rejection is final;
- one open action per object;
- idempotent requests;
- exactly-once execution;
- restart persistence;
- crash resume of approved-but-unexecuted actions.

**Audit.** `engine/commercial/commercial_audit.py`. It is append-only: there is no update or delete API, and triggers abort UPDATE and DELETE. A SHA-256 hash chain lets `verify()` detect tampering, including after the triggers are dropped. **It is not cryptographically immutable**: a party with write access to the file can rebuild a consistent chain. Anchoring the head hash externally is an open item.

**History, statements and receipts.**
- **History:** `engine/commercial/collection_history.py` records each state reached once. Terminal events add history, and the original settlement is retained.
- **Receipts:** `engine/reporting/commercial_receipts.py` issues PAID receipts only with SETTLED status, a settlement reference, a ledger transaction and a reconciliation timestamp. Receipt ids and timestamps are deterministic. Adjustment receipts reference the original PAID receipt.
- **Statements:** `engine/reporting/commercial_statements.py` produces deterministic statements that count as paid only money that is both settled and reconciled, and that refuse other customers' records. No balance-due claim is made.

## Control evidence — operator web authentication (COM-011)

**Identity and credential store.** `dashboard/auth/css_sign_on.py` remains the single canonical operator user store (`data/users.json`); no second identity provider was introduced. Password hashing was upgraded from unsalted SHA-256 to salted PBKDF2-HMAC-SHA256 (600,000 iterations, 16-byte salt, `pbkdf2_sha256$<iterations>$<salt>$<hash>` format). `verify_password()` still accepts a legacy unsalted digest so pre-existing records keep working, and `authenticate_credentials()` transparently rehashes to the new format on the next successful login (`needs_password_rehash`) — verified by `test_authenticate_credentials_upgrades_legacy_hash_on_successful_login` / `..._does_not_upgrade_hash_on_failed_login`. The password-history reuse check (`validate_new_password`) was updated to verify against historical hashes rather than compare hash strings, which is required now that hashing is salted (two hashes of the same password no longer match byte-for-byte).

**Session issuance.** `backend/app/auth/operator_login_router.py` adds `POST /auth/operator/login`, `POST /auth/operator/change-password`, `POST /auth/operator/logout` and `GET /auth/operator/me`, mounted into the real operator web dashboard (`dashboard/web/web_app.py`). Login verifies the password via `css_sign_on.authenticate_credentials` (inheriting its existing lockout-after-3-attempts and password-expiry policy unchanged) and, on success, issues a bearer session token through the pre-existing `backend/app/auth/token_store.TokenStore` — the same store the commercial governance API already resolved sessions against. The caller's `user_id` and `role` in the response always come from the stored record; a client-supplied `role` field is ignored (`test_client_supplied_role_field_is_ignored`). A freshly created operator cannot sign in until they complete `change-password` (`test_newly_provisioned_operator_must_change_password_before_login_succeeds`) — this was already `css_sign_on`'s policy for all callers, not a new restriction.

**Closing the unauthenticated commercial-trial routes.** `dashboard/runtime/trial_contract_router.py` previously accepted `customer_id` in the request body with zero authentication on all four routes (`agreement`, `enroll`, `cancel`, `status`) — anyone who knew or guessed a `customer_id` could enroll or cancel their trial. Two new commercial permissions were added (`commercial_trial_enroll`, `commercial_trial_cancel`, granted to FINCON and HEAD_FINCON only) and the router now requires a valid bearer session for every route: `commercial_view_obligations` for the two read routes, the new permissions for enroll/cancel. The per-route authorization logic was extracted out of `commercial_governance_router.py` into a shared, reusable helper (`engine/commercial/commercial_authorization.actor_from_bearer`) so both routers enforce identically and there is still exactly one commercial role model (`PermissionEngine`/`COMMERCIAL_ROLE_GRANTS`) — not a second one bolted onto the trial router.

**CSRF.** These routes take a bearer token in the `Authorization` header, never a cookie; a browser does not attach that header to a cross-site request automatically, so the classic cookie-CSRF class of attack does not apply here. No CSRF middleware was added because none is needed for this authentication shape — this reasoning should be revisited if a cookie-based session is ever added to `dashboard/web/web_app.py` itself (see limitation 3 below).

**Tests (`tests/test_operator_authentication.py`, 30 cases).** Positive: correct login issues a session with the real stored role; `change-password` on a forced-first-login account issues a working session; a role actually granted a permission can reach the corresponding trial route. Negative: wrong password, unknown user, lockout after repeated failures, missing/malformed/forged/tampered `Authorization` header (all 401), logout revokes the token (subsequent use is 401), a valid session with the wrong role is rejected on enroll/cancel (403, not 401 — proving the 401/403 split is on identity-vs-permission, not conflated), wrong current password on `change-password` (401). No test asserts on a client-supplied role being honored; `test_client_supplied_role_field_is_ignored` asserts the opposite.

**DEV/UAT identities.** `scripts/provision_dev_uat_operators.py` creates FINCON, HEAD_FINCON, AUDIT and HEAD_COMPLIANCE accounts (user ids `10001`–`10004`) with randomly generated passwords (`secrets.token_urlsafe(18)`), each forced to change password on first sign-in. Generated passwords are written once to `artifacts/dev_uat_operator_credentials.json` (gitignored, never printed to a log, never committed) and the script is idempotent (skips accounts that already exist). Run and verified locally on `df566eee`'s successor state; not run against, and must never be pointed at, a production store.

## Control evidence — full commercialization-perimeter closure (COM-012)

**Audit method.** An exhaustive route-by-route audit was run over every router mounted in `dashboard/web/web_app.py`'s `create_app()` (not sampled) before writing any fix, recording per route: auth today, raw-ID-no-scope-check, read-vs-mutation, maker-checker, audit logging. Findings drove every fix below; nothing was fixed speculatively.

**Mission Control and the dashboard-state/WebSocket feed had zero authentication.** `dashboard/runtime/api_bridge.py`'s `create_dashboard_state_router()` (`/api/v1/mission-control`, `/api/v1/broker-state`, `/api/v1/dashboard-state`, `/api/v1/frontend-state`, `/api/v1/positions`, `/api/v1/risk`, `/api/v1/governance`, `/api/v1/opportunities`, `/api/v1/broker`, `/api/v1/broker-reconciliation`, `/api/v1/broker-continuity`, `/api/v1/questrade/account-summary`, `/api/v1/session10-readiness`, `/api/v1/runtime-health`, `/api/v1/runtime-alerts`) and `dashboard/runtime/ws_bridge.py`'s `/ws/v1/dashboard-state` returned live broker cash/equity/positions/PnL/reconciliation state to any unauthenticated caller. A new shared dependency, `backend/app/auth/session_dependency.py` (`require_operator_session` for HTTP, `resolve_operator_session_ws` for the WebSocket handshake), now gates every route on that router (`APIRouter(dependencies=[Depends(require_operator_session)])`) and closes the socket with code 4401 before `accept()` if the session is missing or invalid. This gate accepts *any* valid operator session (cookie or bearer), not a specific commercial permission — it is a general trading-operations view, and requiring a commercial permission here would perversely lock out TRADER/RISK/ADMIN roles who have none by design while admitting only FINCON/AUDIT. `dashboard/web/web_app.py`'s own `/api/v1/margin-snapshot` got the same gate.

**The dashboard HTML pages had zero authentication**, unlike their `dashboard/mobile/mobile_app.py` sibling (which already gates every page via a cookie session — that existing, working pattern is what this borrows the shape of, backed by the *same* `token_store` rather than a second one). `/dashboard`, `/positions`, `/execution`, `/risk-governance`, `/market-opportunities`, `/broker`, `/margin`, `/billing`, `/trial-contract`, `/commercialization-operations` now redirect an anonymous visitor to `GET /login` (a fixed path, no `next=`/return-url parameter — the audit found no existing safe pattern for that in this codebase to reuse, so none was invented; adding one is a separate follow-up, not a blocker). `POST /login` and `POST /logout` in `dashboard/web/web_app.py` authenticate via the same `css_sign_on`/`token_store` machinery as the JSON API and set/clear an HttpOnly, SameSite=Lax session cookie (`css_operator_session`; `Secure` unless `CSS_ENV=development`). No role is ever read from the request — role comes from the session, resolved server-side, in every code path.

**Client-earnings router had the clearest IDOR pattern, including one route with no scoping at all.** `dashboard/runtime/client_earnings_router.py`'s five routes took `policy_id`/`account_reference`/`terms_id` as unchecked query params and returned real customer financial data (realized profit, fees, invoice/receivable ids) to anyone; `GET /api/v1/client-earnings-history` had **no required params whatsoever** and would return every customer's earnings history in one anonymous call. All five now require a bearer session holding `commercial_view_obligations` (FINCON, HEAD_FINCON, AUDIT, HEAD_AUDIT, COMPLIANCE, HEAD_COMPLIANCE), via the same `actor_from_bearer` helper COM-011 introduced.

**Six more commercialization-readiness routers had the same raw-ID/no-auth pattern**, each now gated the same way: `production_charging_router.py`, `commercialization_release_router.py`, `commercialization_operations_router.py`, `payment_collection_preflight_router.py`, `notification_delivery_preflight_router.py`, `launch_dossier_router.py` (an unauthenticated *export* keyed only by a guessable `dossier_id` — the single highest-severity finding in this family). `report_export_router.py` (no per-customer ID, but an unauthenticated export of the same operational state Mission Control exposes) now requires any valid operator session, same rationale as Mission Control.

**Trial enroll/cancel now go through the existing maker-checker engine instead of executing directly** (closes limitation 3 from COM-011). `engine/commercial/commercial_controls.py` gained two new `ControlledActionType`s, `ENROLL_TRIAL` and `CANCEL_TRIAL` (`trial_enrollment_action`/`trial_cancellation_action`), registered onto the *same* action-type registry the reconciliation-exception flow uses (`commercial_controls_from_env`, factored out of `commercial_governance_router_from_env` specifically so nothing registers action types twice). `POST /api/v1/commercial-trial/enroll` and `.../cancel` now call `controls.request(...)` (a FINCON/HEAD_FINCON maker proposes) and return a `PENDING` controlled action rather than an immediate result; approval happens through the *existing, unmodified* `POST /api/v1/commercial/controlled-actions/{id}/approve` endpoint in the commercial governance API — no new approval endpoint was written. This means trial actions inherit, for free, every maker-checker property already proven for reconciliation exceptions: self-approval denial, wrong-role denial, payload-hash tamper detection, exactly-once execution, and restart recovery (`commercial_controls_from_env` rebuilt from the same db_path finds the same `PENDING` action).

**Password change now revokes every other session for that operator.** `backend/app/auth/token_store.TokenStore.revoke_all_for_user()` is called before issuing the new session in `POST /auth/operator/change-password`, so a compromised-password scenario can't leave old sessions usable.

**A pre-existing dependency issue was found and avoided, not routed around:** `dashboard/web/web_app.py`'s login form initially used Starlette's `Request.form()`, which requires the `python-multipart` package even for plain urlencoded bodies — not installed here, and adding it purely for a two-field login form was unwarranted. Reused `dashboard/mobile/mobile_app.py`'s existing dependency-free `_read_form` (`urllib.parse.parse_qs` over the raw body) instead, which is already exercised in production by the mobile app.

**A test-isolation footgun was fixed as it was hit:** `backend/app/auth/session_dependency.py`'s first draft did `from .token_store import token_store` at module level, which freezes a stale reference and silently ignores a test's monkeypatched `token_store` singleton — the same class of bug already avoided in `commercial_governance_router.token_store_session_resolver` (a local import inside the function). Fixed by making the lookup local/dynamic, matching the existing correct pattern, and the same fix was applied to `dashboard/web/web_app.py`'s login/logout handlers.

**Tests.** `tests/test_dashboard_session_auth.py` (52 cases): every protected HTML page redirects anonymously and renders with a valid cookie; the login form sets a working cookie and a wrong password never sets one; logout clears the cookie and revokes the token; Mission Control and every dashboard-state path both reject anonymous/forged-cookie access and accept a valid one; client-earnings routes reject anonymous access, reject a role with no commercial grant (403, not 401), and accept AUDIT. `tests/test_commercialization_readiness_routers_auth.py` (26 cases): the same anonymous/forged/wrong-role/correct-role matrix across all six remaining routers plus report-export. `tests/test_operator_authentication.py` gained 6 maker-checker cases: maker cannot approve their own trial enrollment, wrong role cannot approve, HEAD_FINCON approval transitions the action exactly once and a replay is rejected with 409, a tampered `expected_payload_hash` is rejected with 422, duplicate idempotency keys replay the same pending action, and a rebuilt `CommercialControls` (simulating a restart) still finds the pending action.

## Control evidence — authorization depth, session hardening, defect closure (COM-013)

**Method.** Before implementing anything, a dedicated research pass answered six precise questions: does the data model support per-operator customer scoping today; is firm-wide commercial visibility deliberate or an oversight; does any customer-to-operator assignment concept exist anywhere; is `mobile_app.py`'s session a mechanical swap onto `token_store`; does report-export ever carry customer-specific data; and exactly which routes the cookie-based `require_operator_session` gate guards, by HTTP method. Findings below are attributed to that pass and cited by file:line; nothing here is guessed.

**Object-level (IDOR) authorization: investigated, found to be a real, currently-open architecture gap — not something this pass invents a fix for.** `unit_code`/`home_branch` on the operator user record (`dashboard/auth/css_sign_on.py:128-129`) are stored and displayed but never used to filter which customers/accounts an operator can see — the one module that gives `unit_code` any access-control meaning at all, `backend/app/security/unit_router.py`'s `resolve_unit_bundle`, gates *screens/modules* (`"engine.*"`, `"risk.*"`), not customers, and is never called from anywhere. No `assigned_operator`/`book_of_business`/`customer_owner`/`relationship_manager` concept exists anywhere in `engine/`, `backend/`, or `dashboard/` — confirmed by exhaustive grep, zero matches. `backend/security/permissions.py`'s own top-of-file comment states the intended shape explicitly: commercial viewing is a *role* boundary ("financial control, audit and compliance"), with no mention of per-customer restriction — firm-wide visibility for these roles is deliberate design (mirroring how real back-office/compliance staff work), not an oversight, and this limitation was already named in COM-012 (see item 7 below). **Cross-object substitution was verified to behave exactly as this design implies**: an authorized FINCON/AUDIT session can request customer A's data, then substitute customer B's identifier, and correctly receives customer B's data (not a 403) — because there is no narrower scope for the permission to check against. This is not silently accepted as fine: inventing a restrictive per-operator customer-assignment scheme with no product requirement behind it would be inventing an architecture, which the task explicitly warned against ("implement the narrowest architecture consistent with existing CSS governance rather than inventing permissive defaults" — the same principle cuts against inventing *restrictive* defaults with no basis, in either direction). **Status: OPEN — architecture decision needed from the business (does CSS want book-of-business scoping for commercial staff?), not an engineering defect.**

**The `advice-profitability-history` unhandled-exception defect is fixed.** Root cause: `dashboard/runtime/client_earnings_router.py`'s `read_advice_profitability_history` called `AdviceProfitabilityHistoryService.list_by_terms_id()` with no exception handling, while `AdviceProfitabilityHistoryService.list_by_terms_id` (`backend/app/persistence/services/advice_profitability_history_service.py:31-32`) *correctly* raises `AdviceProfitabilityError` for an unknown `terms_id` — the service's behavior was already right; only the router failed to catch it, producing an unhandled 500 instead of a clean 404. Fixed by catching `AdviceProfitabilityError` and returning 404 with the exception's own message (`dashboard/runtime/client_earnings_router.py`). The same exception type also covers a malformed `terms_id` (same not-found code path) and a broken canonical chain — all now 404, none leak a stack trace. Exposing the specific reason string to the caller is deliberate, not an information-disclosure risk: the endpoint is authenticated and role-gated (`commercial_view_obligations`) before this code ever runs, so the caller is already an authorized compliance/audit operator who needs the real reason for troubleshooting, not an anonymous prober. **Tests (`tests/test_advice_profitability_history_router.py`, 5 cases): unknown terms_id → 404; malformed terms_id → 404; known terms_id + authorized role → 200 with correct data (seeded via the same fixture pattern as the existing service-level unit test); known terms_id + unauthorized role → 403; response body contains no stack trace / file path. Status: AUTOMATED-TEST VERIFIED.**

**Browser/commercial auth unification: investigated, not done — the investigation itself is the deliverable for this pass.** Confirmed precisely which routes `require_operator_session`/`resolve_operator_session*` guard: all 15 routes in `dashboard/runtime/api_bridge.py`'s dashboard-state router, the one route in `report_export_router.py`, the one WebSocket handshake, and every HTML page in `web_app.py` — **every one of them is a GET (or the WebSocket handshake); none is a mutating commercial-permission route.** The five commercial-permission POST routes (`commercial_governance_router.py` x3, `trial_contract_router.py` x2) remain bearer-header-only, unchanged. Migrating them to accept a cookie too is mechanically straightforward (swap `Header(default=None)` for a `Request` param and call the same token-extraction helper) but was **not done this pass**, deliberately: it would touch route signatures in `commercial_governance_router.py` that are already CI-verified on PR #100 with no concrete UI need driving the change yet (no page's embedded JavaScript currently calls any of these five routes). **Status: OPEN — investigated and scoped, not implemented; low risk to defer since no bearer→cookie security regression exists (bearer-only is strictly more restrictive, never less, than cookie-or-bearer).**

**Mobile session unification: investigated, determined NOT to be a safe mechanical swap — documented, not forced.** `dashboard/mobile/mobile_app.py`'s session dict (`_create_session`, lines 607-615) stores `created`, `last_activity`, and a full `user_ctx` copy (`user_id`, `display_name`, `role`, `unit_code`, `home_branch`). `token_store.SessionInfo` carries only `username`, `roles` (a list), `issued_at_utc`, `expires_at_utc` — no `display_name`, `unit_code`, or `home_branch`, all three of which mobile's page handlers actively read on every request (e.g. `_dashboard_page(user_ctx=user_ctx, ...)`). ## Control evidence — mobile CSRF closure and authentication audit trail (COM-014)

**Mobile CSRF: closed with a session-bound synchronizer token, enumerated exhaustively first.** Every `@app.post` route in `dashboard/mobile/mobile_app.py` was enumerated (7 total): `POST /login` (the auth action itself — no session exists yet, classic CSRF doesn't apply), `POST /password-change` (a short-lived possession cookie from the forced-first-login flow, not the main session — but a forced password change is a full account-takeover primitive, so protected the same way), `POST /logout` (cookie-gated, state-changing, but the worst outcome is forcing a logout — same low-severity reasoning already applied to `web_app.py`'s `/logout` in COM-012/013, left on SameSite=Lax alone, deliberately, not by oversight), and the three genuinely high-severity ones COM-013 flagged: `POST /controls` (can arm mobile live trading), `POST /trade` (submits a trade ticket), `POST /users` (creates operator accounts).

For the four protected routes (`/controls`, `/trade`, `/users`, `/password-change`), `_create_session` and `_create_password_change_token` now each mint a `secrets.token_urlsafe(32)` CSRF token alongside the session/possession token — server-generated, session-bound (rotates on every new login, dies the instant the session does), embedded as a hidden form field (`_csrf_field`), and checked with `secrets.compare_digest` (`_verify_csrf`) before any role check or business logic runs. A missing, wrong, or cross-session token is rejected with 403 before the route's own authorization check ever executes — proven by `test_valid_csrf_token_without_required_role_is_rejected`, which shows a *matching* CSRF token alone is still not sufficient without the right role. No token is ever placed in a URL or accepted from a query string; failure responses re-embed the *current* valid token (needed so the user's own retry can succeed — the attacker who triggered a cross-site request never gets to read this response, so this is not a leak) but never the session token itself. `/trade`'s pre-existing authorization model (report denial via a 200 response body rather than an HTTP 403) was left as-is — CSRF now correctly gates the request into that pre-existing check without changing what happens after.

**Tests (`tests/test_mobile_csrf.py`, 31 cases).** The full requested negative matrix, parametrized across `/controls`, `/trade`, `/users`: anonymous request (redirected, never executed), cookie without CSRF token, invalid token, token from another session, valid token without the required role (rejected independently of CSRF — not a substitute for authorization), expired session with a valid-looking token, revoked session with a token, valid authorized session with a matching token (accepted). Plus: CSRF token replay after logout is rejected (session gone, token useless), a new login rotates both the session token and the CSRF token, and the full password-change matrix (missing/invalid/cross-flow token rejected, valid token succeeds) separately since it uses its own possession-token record rather than a full session. A dedicated check confirms a CSRF-failure response never contains the raw session token or a stack trace.

**Authentication / account-lifecycle audit trail: added, reusing the existing architecture.** `backend/app/auth/auth_audit.py` wraps the same `CommercialAuditLog` class the commercial governance API already uses (append-only, SHA-256 hash-chained) — not a parallel logging subsystem — pointed at its own database (`data/css_auth_audit.sqlite3` by default, overridable via `CSS_AUTH_AUDIT_DB`) so it captures events in every deployment, independent of whether `CSS_COMMERCIAL_DB` (commercial governance) happens to be configured; unlike that one, this is on by default since login/logout/lockout auditing is baseline hygiene, not an opt-in commercial capability. Logging is best-effort and never raises — an audit-write failure (disk full, locked file) cannot block or fail the authentication action it describes.

Wired into the actual chokepoints so every caller gets coverage automatically, not per-router boilerplate: `dashboard/auth/css_sign_on.py`'s `authenticate_credentials` (LOGIN_SUCCESS incl. the PASSWORD_CHANGE_REQUIRED variant, LOGIN_FAILURE for unknown/malformed user id, wrong password, account-disabled, and active-lockout attempts, ACCOUNT_LOCKOUT on the triggering failure) and `change_password` (PASSWORD_CHANGE) — both used by `mobile_app.py`, `operator_login_router.py`, and the console/GUI entry point alike, so this is genuinely universal, not per-caller. `set_user_disabled` logs ACCOUNT_DISABLED/ACCOUNT_ENABLED and AUTHORIZATION_DENIED for a non-super-user attempt. `backend/app/auth/session_dependency.py`'s `revoke_session_from_request` (shared by both `web_app.py`'s and `operator_login_router.py`'s `/logout`) logs LOGOUT with the resolved actor/role; `mobile_app.py`'s separate logout (its own session store, not `token_store`) got its own matching call since it isn't reachable through that shared helper. `token_store.TokenStore.revoke_all_for_user` logs SESSION_REVOKE_ALL with the actual count revoked. The admin disable/enable router additionally logs AUTHORIZATION_DENIED at its own gate (not just inside `set_user_disabled`), since the router does its own pre-check before ever calling into `css_sign_on` and would otherwise never exercise that internal log path.

**User-enumeration care.** An unknown-user login attempt is logged server-side with full detail (`UNKNOWN_USER`) for real security visibility, but the client-facing `AuthFailure` message and HTTP behavior are unchanged from before this pass — logging is one-way (server-side only) and never surfaces through the response, so it does not create or worsen any enumeration side channel.

**Tests (`tests/test_auth_audit_events.py`, 11 cases).** Exactly one event per action, not duplicates: successful login, failed login (wrong password and unknown user, separately), lockout after repeated failures (distinct from a disabled-account attempt, which logs its own outcome and never reaches lockout logic), logout, password change together with the session-revocation count it triggers, account disable and enable (one event each), a non-super-user disable attempt logged as AUTHORIZATION_DENIED. A dedicated test greps every recorded event's `details`/`reason` for five different secret forms (the raw bearer token, both plaintext passwords used in the test, the stored password hash, and an independently-computed legacy hash) and asserts none appear. A final test runs the shared hash-chain `verify()` over the auth-audit database and confirms no duplicate `event_id`s — the same append-only/tamper-evident semantics as the commercial audit log, not a weaker parallel one; **not** described as externally immutable, since no external anchoring exists for this database either.

**Account disable/enable governance: re-audited.** Ordinary operators (tested with AUDIT) cannot call the admin endpoints (403, COM-013); only SUPER_USER can. Disabling revokes every existing session immediately (`/me` → 401) and blocks a fresh login. Re-enabling restores the ability to log in but **does not resurrect the pre-disable session** — confirmed by `test_re_enabled_account_gets_a_fresh_session_not_an_old_one`, which shows the old token stays dead and a fresh login issues a genuinely new one. Duplicate disable and duplicate enable are both safely idempotent (same 200, same resulting state, no error). An unknown target user id fails cleanly with 404, not a 500 or a silent no-op. No maker-checker was added for disable/enable: `create_user` — an equally or more sensitive identity-administration action — has never required a second approver anywhere in this codebase (it's a single SUPER_USER action in both `mobile_app.py` and `css_sign_on.py`), so requiring one only for disable/enable would be inventing a new governance policy with no existing precedent to justify it, not closing a gap. **Status: AUTOMATED-TEST VERIFIED**, maker-checker requirement **OPEN — PRODUCT/ARCHITECTURE DECISION** if the business wants to establish one going forward (for identity administration generally, not just disable/enable).

**WebSocket revalidation: reconfirmed as bounded-interval, not message-driven, and stress-tested for the idle case explicitly.** The revalidation check added in COM-013 runs at the top of every `while True` loop iteration, gated only by `asyncio.sleep(interval_seconds)` (the same 5-second timer already driving data refresh) — it is not conditioned on any incoming client message (this socket is server-to-client only) or on there being new data to send, so an "idle" period (no data changes, only heartbeats) re-validates on exactly the same schedule as an "active" one; there is no separate, more aggressive timer adding load to the session store. `test_revalidation_happens_on_every_tick_not_just_once` proves this directly: the connection survives two clean ticks and closes precisely on the third, when the token is revoked. `test_account_disabled_mid_stream_closes_the_connection` mirrors the real admin-disable flow (`revoke_all_for_user`, exactly what the disable endpoint calls) rather than a bare token revoke, to prove the disable path specifically — not just revocation in the abstract — closes an open socket.
